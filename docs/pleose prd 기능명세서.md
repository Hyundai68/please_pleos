# 오는 길에 부탁해 — PRD 및 기능명세서

# Part 1. PRD

## 1. 개요

'오는 길에 부탁해'는 가족이 앱으로 보낸 부탁을 운전 중인 플레오스 차량이 음성으로 알려주고, 경로 위에서 처리하도록 안내한 뒤 완료까지 공유하는 서비스입니다.

### 제품 목표

- 운전자가 휴대폰을 보지 않고 가족의 부탁을 받고 처리하게 한다.
- 부탁을 이해해 내 경로 위에서 가장 부담 없는 방법으로 해결하게 한다.
- 부탁의 진행 상태를 가족이 연락 없이 알 수 있게 한다.

### 부탁 유형

| 유형 | 예시 |
| --- | --- |
| 사 와줘 | 해열제, 우유, 저녁 반찬 |
| 받아 와줘 | 포장 주문, 세탁소 옷, 편의점 택배 |
| 데려와줘 | 학원 끝난 아이, 역에 있는 배우자 |
| 들러줘 | 부모님 댁 반찬, 반찬통 반납, 반품 접수 |

### 비목표 (이번 범위가 아닌 것)

- 차 안에서의 주문·결제 처리
- 매장 광고나 유료 순위 노출
- 가족 간 실시간 위치 추적

## 2. 타깃 사용자와 페르소나

서비스에는 두 역할이 있습니다. 같은 사람이 상황에 따라 두 역할을 오갑니다.

| 역할 | 정의 | 사용 환경 |
| --- | --- | --- |
| **수행자 (운전자)** | 부탁을 받아 처리하는 사람 | 플레오스 차량, 운전 중 음성 중심 |
| **요청자 (가족)** | 부탁을 보내는 사람 | 스마트폰 앱 |

### 페르소나 1: 지훈 (수행자)

- 30대 후반, 맞벌이, 다섯 살 아이 아빠. 플레오스 탑재 차량으로 출퇴근한다.
- 퇴근길 운전 중 아내의 카톡을 확인하지 못해 집 근처에서 약국으로 되돌아간 적이 많다.
- 원하는 것: 운전에 집중하면서도 가족 부탁을 놓치지 않는 것.

### 페르소나 2: 수진 (요청자)

- 30대 중반, 맞벌이. 먼저 퇴근해 아이를 돌본다.
- 운전 중인 남편에게 전화하기 부담스럽고, 부탁이 전달됐는지, 처리됐는지 몰라 다시 연락하게 된다.
- 원하는 것: 부탁하고 잊어도 되는 것, 결과를 확인할 수 있는 것.

### 확장 사용자

부모님을 병원에 모시는 40~50대, 아이 학원 픽업이 잦은 초등 학부모, 차 한 대를 함께 쓰는 신혼부부.

## 3. 문제 정의와 사용자 스토리

가족의 부탁은 메신저로 오지만, 받는 사람은 운전 중이라 확인도 처리도 어렵고, 보낸 사람은 결과를 알 수 없습니다.

### 문제

| 문제 | 영향 |
| --- | --- |
| 운전 중 메시지 확인 불가 | 부탁을 놓치거나 위험하게 확인 |
| 부탁 처리 장소를 따로 찾아야 함 | 되돌아가기, 마감 시간 놓침 |
| 픽업 위치·시간 엇갈림 | 운전 중 반복 통화 |
| 처리 결과 공유 안 됨 | 중복 구매, "했어?" 재연락 |

### 사용자 스토리

**요청자**

- 요청자로서, 운전 중인 가족에게 전화하지 않고 부탁을 보내고 싶다. 운전을 방해하지 않기 위해서다.
- 요청자로서, 부탁이 전달됐는지, 진행 중인지, 끝났는지 알고 싶다. 다시 연락하지 않기 위해서다.
- 요청자로서, 아이 픽업을 부탁할 때 도착 예정 시각을 알고 싶다. 아이를 제때 준비시키기 위해서다.

**수행자**

- 수행자로서, 운전 중에 부탁을 음성으로 듣고 음성으로 답하고 싶다. 휴대폰을 보지 않기 위해서다.
- 수행자로서, 부탁을 처리할 곳을 내 경로에서 자동으로 찾아주길 원한다. 따로 검색하거나 되돌아가지 않기 위해서다.
- 수행자로서, 들를 수 없을 때 간단히 거절하고 싶다. 무리하지 않고 가족에게 알리기 위해서다.
- 수행자로서, 부탁이 여러 개면 한 번에 묶어서 효율적인 순서로 안내받고 싶다.

## 4. 성공 지표

지표는 차량 판매 기여가 아니라 이용자가 체감하는 가치로 잡습니다. 목표치는 MVP 파일럿 후 확정합니다.

| 구분 | 지표 | 정의 | MVP 목표 (가정) |
| --- | --- | --- | --- |
| 핵심 | 부탁 완료율 | 수락된 부탁 중 완료 처리된 비율 | 80% 이상 |
| 핵심 | 가족 주간 재사용률 | 한 주에 1건 이상 부탁을 주고받은 가족 그룹 비율 | 50% 이상 |
| 안전 | 주행 중 화면 조작 | 주행 중 부탁 처리 과정의 화면 터치 수 | 0회 |
| 효율 | 우회 시간 | 경유지 추가로 늘어난 평균 주행 시간 | 5분 이내 |
| 효율 | 수락 응답 시간 | 음성 알림 후 수락·거절까지 걸린 시간 | 10초 이내 |
| 신뢰 | 재연락 감소 | 부탁 후 같은 건으로 전화·메시지를 다시 보낸 비율 (설문) | 파일럿 전 대비 감소 |

## 5. 범위, 제약과 가정, 리스크

### MVP 범위

| 포함 | 제외 (이후 단계) |
| --- | --- |
| 가족 그룹 생성·초대 | 차 안 주문·결제 |
| 네 가지 부탁 유형 전송 | 매장 실시간 재고 연동 |
| 차량 음성 알림과 음성 수락·거절 | 포장·세탁소 준비 상태 연동 |
| 부탁 품목 → 장소 종류 매칭, 경로상 장소 추천 | 반복 부탁(정기 루틴) |
| 경유지 자동 추가와 다중 부탁 순서 최적화 | 트렁크 속 물건 알림 |
| 완료 확인과 상태 공유 | 해외 매장 정보 |
| 데려와줘 도착 예정 시각 공유 |  |

### 제약과 가정

- **플레오스 API 가정**: 내비게이션 경로·도착 예정 시각, 경유지 추가, 차량 주행 상태(주행/정차/주차), 음성 에이전트 연동이 앱에 열려 있다고 가정합니다. 공모전 개발 문서로 확인이 필요합니다.
- **주행 중 조작 제한**: 주행 중 화면 입력은 쓰지 않고 음성으로만 처리합니다.
- **장소 정보**: MVP는 공개 지도·장소 정보의 영업시간과 업종을 사용합니다.

### 리스크

| 리스크 | 대응 |
| --- | --- |
| 부탁 문장 해석 오류 ("그거 사와") | 해석 결과를 음성으로 되묻고, 애매하면 요청자에게 품목 확인 요청 |
| 장소 영업시간 정보 부정확 | 도착 시점 기준 영업 여부를 보수적으로 판단, 마감 임박 시 안내 |
| 운전 집중 방해 | 고속도로 합류 등 주의 구간에서는 알림을 미뤘다가 안전 구간에서 전달 |
| 픽업 관련 개인정보 우려 | 위치 대신 도착 예정 시각만, 요청자에게만, 탑승 전까지만 공유 |

## 7. 기능 상세 명세

P0 기능 중 핵심 흐름을 이루는 기능의 상세입니다.

### F-02 부탁 작성·전송

| 항목 | 내용 |
| --- | --- |
| 트리거 | 요청자가 앱에서 "부탁하기" 선택 |
| 입력 | 유형(사 와줘/받아 와줘/데려와줘/들러줘, 미선택 시 자동 분류), 내용, 장소(받아 와줘·데려와줘·들러줘는 필수), 시간(데려와줘는 필수), 급함 여부, 받을 사람 |
| 처리 | 필수값 검증 → 부탁 생성(상태: 생성됨) → F-03 라우팅 호출 |
| 출력 | 요청자 화면에 "전달 중" 표시 |
| 예외 | 받을 사람이 차량 미연결 → 앱 푸시로만 전달하고 요청자에게 안내 |

### F-03 부탁 전달 라우팅 · F-04 차량 음성 알림

| 항목 | 내용 |
| --- | --- |
| 트리거 | 부탁 생성 |
| 입력 | 수행자의 차량 주행 상태, 현재 경로, 주의 구간 여부 |
| 처리 | 주행 중이면 차량 음성으로, 정차·미운행이면 앱 푸시로 전달. 주의 구간(합류, 교차로 진입 직전)이면 안전 구간까지 알림 보류 |
| 출력 | 음성: "[요청자]님이 [내용]을 부탁했어요. [추천 장소] 우회 [n]분이에요. 안내할까요?" |
| 예외 | 추천 장소 없음 → "경로 근처에 영업 중인 곳이 없어요. 나중에 알려드릴까요?" |

### F-05 음성 수락·거절

| 응답 | 처리 |
| --- | --- |
| "응", "안내해줘" | 수락 → F-08 경유지 추가, 요청자에게 "수락" 공유 |
| "다른 곳" | 다음 후보 장소 안내 |
| "나중에" | 보류, 집까지 남은 경로 중 다음 적절한 시점에 재알림 |
| "못 가", "오늘은 안 돼" | 거절, 요청자에게 "오늘은 어렵대요" 공유 |
| 무응답 10초 | 보류 처리 후 정차 시 화면으로 재안내 |

### F-06 부탁 해석 · F-07 경로상 장소 추천

| 항목 | 내용 |
| --- | --- |
| 입력 | 부탁 문장, 현재 위치, 목적지까지 경로, 도착 예정 시각 |
| 처리 | ① 문장에서 품목·행동 추출 → ② 장소 종류 매칭(약 → 약국, 우유 → 편의점·마트) → ③ 경로 주변 후보 검색 → ④ 도착 시점 영업 여부·주차 가능 여부로 필터 → ⑤ 우회 시간이 짧은 순으로 정렬 |
| 순위 원칙 | 우회 시간, 영업 여부, 주차 가능 여부만 사용. 유료 노출로 순위를 바꾸지 않음 |
| 예외 | 품목이 모호하면 음성으로 되묻기, 해석 실패 시 요청자에게 품목 확인 요청 |

### F-08 경유지 자동 추가·순서 최적화

| 항목 | 내용 |
| --- | --- |
| 처리 | 수락한 장소를 경유지로 추가. 여러 건이면 시간 제약(데려와줘 시각, 매장 마감)을 먼저 맞추고 나머지는 총 우회 시간이 최소가 되게 정렬 |
| 출력 | "태권도 먼저 들르고 김밥집으로 갈게요" 음성 안내 |
| 예외 | 시간 제약을 모두 맞출 수 없으면 맞출 수 없는 부탁을 알리고 선택 요청 |

### F-09 완료 확인

| 유형 | 완료 기준 |
| --- | --- |
| 사 와줘 · 받아 와줘 · 들러줘 | 경유지 도착 후 출발 감지 → "[품목] 챙겼어요?" 음성 확인 → "응"이면 완료 |
| 데려와줘 | 경유지 정차 후 문 열림·닫힘 감지와 출발 → 완료 (음성 확인 생략 가능) |
| 공통 예외 | "못 샀어" → 다음 후보 장소 제안 또는 요청자에게 "못 샀대요" 공유 |

### F-11 픽업 도착 예정 공유

| 항목 | 내용 |
| --- | --- |
| 대상 | 데려와줘 부탁의 요청자에게만 |
| 공유 정보 | 도착 예정 시각, 정차 지점. 실시간 위치 좌표는 공유하지 않음 |
| 공유 기간 | 수락 시점부터 탑승 완료까지, 완료 즉시 종료 |
| 갱신 | 도착 예정 시각이 3분 이상 바뀔 때만 갱신 |

## 8. 부탁 상태 흐름

| 완료 | 완료 |

## 9. 음성 대화 설계와 주행 중 UX 정책

### 대화 원칙

- 한 번의 안내는 15초 이내, 질문은 한 번에 하나만 합니다.
- 답은 "응 / 다른 곳 / 나중에 / 못 가" 네 가지로 끝나게 묻습니다.
- 요청자 이름을 먼저 말해 누구의 부탁인지 바로 알게 합니다.

### 유형별 대표 스크립트

| 상황 | 차량 음성 |
| --- | --- |
| 사 와줘 | "수진님이 아이 해열제를 부탁했어요. 경로상 ○○약국이 우회 2분이고 9시까지 열어요. 안내할까요?" |
| 받아 와줘 | "지훈님이 ○○김밥 포장을 받아 와 달래요. 우회 3분이에요. 경유지로 넣을까요?" |
| 데려와줘 | "지훈님이 5시에 태권도장에서 아이를 데려와 달래요. 지금 가면 5시 2분 도착이에요. 안내할까요?" |
| 들러줘 | "어머님이 반찬을 챙겨두셨대요. 지금 경로에서 우회 6분이에요. 들를까요?" |
| 여러 건 | "부탁이 2개 있어요. 태권도 먼저, 김밥집은 그다음이 빨라요. 이렇게 갈까요?" |
| 완료 확인 | "해열제 챙겼어요?" |

### 주행 중 UX 정책

| 상태 | 허용 | 제한 |
| --- | --- | --- |
| 주행 중 | 음성 알림, 음성 응답, 경유지 자동 추가 | 부탁 목록·지도 상세 화면, 텍스트 입력 |
| 주의 구간 (합류, 교차로 직전, 고속 주행) | 없음 (알림 보류) | 모든 알림 |
| 정차·주차 | 부탁 목록 화면, 부탁 상세, 다른 장소 선택 | 없음 |
